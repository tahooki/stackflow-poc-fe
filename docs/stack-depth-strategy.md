# 스택 깊이 성능 전략

Stackflow 스택은 깊이가 너무 커지면 느려지거나 불안정해질 수 있다.
이 문서는 느려짐을 방지하고 네비게이션을 안정적으로 유지하는 옵션을 정리한다.

## 목표
- 스택이 깊어져도 네비게이션 응답성을 유지한다.
- 가능한 범위에서 기대 UX(뒤로가기 + 스크롤 복원)를 보존한다.
- 한계에 도달했을 때 예측 가능한 폴백 동작을 제공한다.
- 옵션형 제어로 기존 플로우를 깨지 않게 한다.

## 문제 신호
- 스택 깊이가 커지면 전환 애니메이션이 버벅이거나 멈춘다.
- 메모리 사용량이 계속 증가하고 뒤로가기 후에도 회복되지 않는다.
- 스크롤 복원이 불안정하거나 시간이 오래 걸린다.
- 렌더링 비용이 스택 길이에 비례해 증가한다.

## 전략 1: 하드 스택 깊이 제한
최대 깊이를 정하고, 초과 시 오래된 항목을 제거한다.

장점
- 단순하고 예측 가능하다.
- 무한한 메모리 증가를 막는다.

단점
- 오래된 히스토리가 사라진다.

추천 정책
- `maxDepth`: 일반 플로우는 10~20 화면.
- `maxDepth` 초과 시 루트를 제외한 가장 오래된 화면부터 제거.

예시 동작
- `root` + 최근 N-1 화면을 유지.
- 유지 범위를 넘어 뒤로가려 하면 `root`로 리다이렉트.

## 전략 2: 소프트 제한 + replace 규칙
반복되는 흐름은 replace 방식으로 네비게이션한다.

사용 사례
- 멀티 스텝 폼(다음 단계가 이전 단계 대체).
- 리스트 -> 상세 -> 상세(동일 타입) 이동.

규칙
- 다음 화면이 같은 `activityName`이면 `push` 대신 `replace`.
- 화면이 `transient`로 표시되면 항상 `replace`.

## 전략 3: 화면 재사용 + 상태 리셋
새 인스턴스를 쌓는 대신 기존 화면을 재사용하고 내부 상태를 리셋한다.

사용 사례
- 검색 결과 화면.
- 파라미터만 다른 필터 리스트.

주의점
- 스크롤 복원은 가치가 있을 때만 유지.
- 파라미터에는 최소 상태(쿼리 + 선택값)만 저장.

## 전략 4: 유휴/백그라운드에서 정리
앱이 유휴 상태일 때 오래된 스택을 정리해 메모리를 회수한다.

아이디어
- `maxAgeMs`보다 오래된 화면 제거.
- 탭이 숨겨졌을 때 `maxDepth` 초과 화면 제거.

## 전략 5: 무거운 화면 지연/스냅샷
화면당 비용을 낮춰 더 깊은 스택을 허용한다.

옵션
- 포커스될 때까지 무거운 데이터 로딩 지연.
- 스켈레톤 + 점진 로딩 사용.
- 스택이 깊으면 비활성 화면 스냅샷 후 언마운트.

## 전략 6: 렌더 예산 가드
깊이에 따라 무거운 컴포넌트를 제한한다.

예시 규칙
- depth > 8이면 차트/비디오/대형 리스트 비활성화.
- depth > 12이면 경량 폴백 UI 렌더.

## 전략 7: 메모리 + 프레임 타임 모니터링
네비게이션 상태를 모니터링해 제한값을 조정한다.

로그 필드
- stackDepth
- transitionDurationMs
- longTaskCount
- memoryUsed (가능할 때)

로그 위치
- Stackflow 플러그인 라이프사이클 훅(push, replace, pop).
- `web-vitals` 커스텀 핸들러에서 long task 추적.

## 권장 기본 정책 (안전한 베이스라인)
- `maxDepth`: 12
- `activityName` 반복 시 replace
- `visibilitychange: hidden` 시 depth 8로 정리
- depth > 8이면 무거운 렌더링 지연

## 정책 예시 테이블

| 조건 | 동작 |
| --- | --- |
| depth > 12 | root + 최근 11개만 유지 |
| 다음 activity 반복 | push 대신 replace |
| depth > 8 | 무거운 UI 비활성 또는 지연 로딩 |
| 탭 hidden | depth 8로 정리 |

## 구현 메모
- 안정 플로우를 깨지 않도록 기능 플래그 뒤에 둔다.
- 깊이 임계값을 앱 설정에서 조정 가능하게 한다.
- 제한을 초과해도 되는 플로우를 문서화한다.
